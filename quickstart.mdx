---
title: "Quickstart"
description: "Run the JWT Secure API locally and make your first authenticated request"
---

<Steps>

<Step title="Prerequisites">

You need the [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) installed on your machine.

Verify your installation:

```bash
dotnet --version
# Should output 10.x.x
```

</Step>

<Step title="Clone and configure">

Clone the repository and navigate into it:

```bash
git clone https://github.com/Black-09/prueba.git
cd prueba
```

The API requires three environment variables at startup. If any are missing the process will exit with a descriptive error message.

<Warning>
`JWT__Key` must be **at least 32 characters** long. It is used as the HMAC-SHA256 signing key. Shorter keys will cause the API to refuse to start.
</Warning>

Export the variables before running:

<CodeGroup>

```bash macOS / Linux
export JWT__Key="your-super-secret-key-minimum-32-chars!!"
export JWT__Issuer="https://localhost:5001"
export JWT__Audience="https://localhost:5001"
```

```powershell Windows (PowerShell)
$env:JWT__Key      = "your-super-secret-key-minimum-32-chars!!"
$env:JWT__Issuer   = "https://localhost:5001"
$env:JWT__Audience = "https://localhost:5001"
```

</CodeGroup>

| Variable | Description |
|---|---|
| `JWT__Key` | HMAC-SHA256 signing secret. Minimum 32 characters. |
| `JWT__Issuer` | Placed in the `iss` claim and validated on every request. |
| `JWT__Audience` | Placed in the `aud` claim and validated on every request. |

<Note>
The double-underscore (`__`) syntax maps to the `Jwt:Key`, `Jwt:Issuer`, and `Jwt:Audience` keys in `appsettings.json`. Environment variables take precedence over the config file.
</Note>

</Step>

<Step title="Run the API">

```bash
dotnet run
```

On first run, the API automatically applies all pending EF Core migrations and creates `app.db` (a SQLite database) in the project directory:

```
info: Microsoft.EntityFrameworkCore.Database.Command[20101]
      Executed DbCommand ... CREATE TABLE "Users" ...
info: Microsoft.Hosting.Lifetime[14]
      Now listening on: https://localhost:5001
```

<Tip>
The SQLite database file `app.db` is created next to the project file. You can inspect it with any SQLite browser to debug token state or user records during development.
</Tip>

</Step>

<Step title="Register a user">

```bash
curl -s -X POST https://localhost:5001/register \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "password": "Secret1!"}' \
  -c cookies.txt
```

A successful registration returns `200 OK` with the body `Usuario creado`.

**Password requirements** — all four rules are enforced. The request returns `400 Bad Request` if any are not met:

| Rule | Requirement |
|---|---|
| Length | Minimum 8 characters |
| Uppercase | At least 1 uppercase letter (`A`–`Z`) |
| Digit | At least 1 numeric digit (`0`–`9`) |
| Symbol | At least 1 non-alphanumeric character (e.g. `!`, `@`, `#`) |

<Warning>
Usernames are limited to 50 characters. Registering a username that already exists returns `400 Bad Request`.
</Warning>

</Step>

<Step title="Login">

```bash
curl -s -X POST https://localhost:5001/login \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "password": "Secret1!"}' \
  -c cookies.txt -b cookies.txt
```

On success the API returns `200 OK` and sets two cookies:

| Cookie | Cookie MaxAge | Description |
|---|---|---|
| `access_token` | 15 minutes | JWT used to authenticate requests (JWT itself expires after `Jwt:ExpiryMinutes`, default 10 min) |
| `refresh_token` | 7 days | Opaque token used to obtain a new access token |

Both cookies are `HttpOnly`, `Secure`, and `SameSite=Strict`. The `-c cookies.txt` flag writes them to disk; `-b cookies.txt` sends them on subsequent requests.

<Note>
After **5 consecutive failed login attempts** the account is locked for **15 minutes**. All login attempts during the lockout window return `401 Unauthorized` with no indication of the remaining lock time, to prevent information leakage.
</Note>

</Step>

<Step title="Access a protected endpoint">

```bash
curl -s https://localhost:5001/secure \
  -b cookies.txt
```

A successful response returns `200 OK` with the body `OK`.

If the `access_token` cookie is missing or expired, the API returns `401 Unauthorized`. Proceed to the next step to refresh it without logging in again.

</Step>

<Step title="Refresh the token">

When the access token expires, exchange the refresh token for a new pair:

```bash
curl -s -X POST https://localhost:5001/refresh \
  -c cookies.txt -b cookies.txt
```

The API performs **refresh token rotation** on every call:

1. The current `refresh_token` is validated and immediately revoked.
2. A new `access_token` (JWT expiry: 10 min default; cookie MaxAge: 15 min) and a new `refresh_token` (7 days) are issued and written back to `cookies.txt`.

<Warning>
If a refresh token is presented after it has already been used — indicating possible token theft — the API revokes **every token in the same token family** and forces the user to log in again. This is refresh token reuse detection.
</Warning>

<Tip>
A token family (`FamilyId`) is created at login and inherited across all rotations within that session. Use `POST /logout-all` to revoke all active tokens for the authenticated user across every device at once.
</Tip>

</Step>

<Step title="Logout">

Revoke the current session and clear both cookies:

```bash
curl -s -X POST https://localhost:5001/logout \
  -b cookies.txt -c cookies.txt
```

The server marks the `refresh_token` as revoked in the database and instructs the client to delete both cookies. Any subsequent request with the old tokens returns `401 Unauthorized`.

To invalidate all sessions across every device at once:

```bash
curl -s -X POST https://localhost:5001/logout-all \
  -b cookies.txt -c cookies.txt
```

</Step>

</Steps>
